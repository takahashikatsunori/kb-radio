1. 全体像 ― AIオーケストレーションで毎朝届くラジオ番組

システム全体の設計思想

このラジオ番組は、人間のスタジオ収録ではなく、Python（パイソン）で組まれた制作システムが毎朝自動で作っています。ただし、「1つのAIに『今日小平市のラジオ台本を書いて』と丸投げする」のではありません。役割ごとに得意なツールやAIモデルを指揮者のように連携させる「AIオーケストレーション」という考え方で作られています。

🔰 かみ砕きメモ：「AIオーケストレーション」ってなに？ オーケストラにバイオリン・トランペット・打楽器それぞれの名手がいて、指揮者がタイミングを合わせて1つの交響曲を作るように、「調べるのが得意なAI」「おしゃべり台本を書くのが得意なAI」「ミスをチェックするAI」「声を出して演技するAI」「計算して音楽を鳴らすプログラム」を組み合わせることで、1人（1つのAI）では絶対に届かない正確さと温かさを実現する仕組みです。

2. ステップ1 ― 今朝の天気・地震・カレンダー・長期記憶を集める

src/live_feeds.py ・ src/schedule_calendar.py

ラジオらしさの命は「まさに今朝の天気」と「昨日の話題と被らない連続性」です。台本を書き始める前に、プログラムは外部の公的・オープンAPIとリポジトリ内の記憶データを一気に集めます。

🔰 かみ砕きメモ：「API（エーピーアイ）」ってなに？ プログラム同士がデータを受け渡しするための「レストランの注文窓口」です。私たちがWebブラウザで天気サイトを目で見て確認する代わりに、Pythonプログラムが https://api.open-meteo.com/... という窓口に注文票を送ると、小平市の気温・湿度・降水確率が整理されたデータ（JSON形式）で1秒以内に返ってきます。

☁ Open-Meteo API（小平市のピンポイント天気）

src/live_feeds.py が小平市中心の緯度・経度（35.7285, 139.4775）を指定して、今朝の気温・湿度・風速・3日間予報を取得。前後の気温差が9℃以上なら「寒暖差注意」、湿度45%以下なら「乾燥・火の元注意」といった番組用アドバイスも自動生成します。

🌋 P2PQuake API v2（緊急地震トリガー）

直近48時間の地震履歴（codes=551）を取得。もし関東・東京で震度4以上、全国で震度5弱以上、または津波警報・注意報を検知した場合は、通常構成に+4分の緊急防災コーナー（special_feature）を自動追加して放送尺を拡張します。

📅 jpholiday ＆ 特別日・事前編成カレンダー

日本の祝日判定ライブラリ jpholiday により、土日だけでなく祝日（例：11/23 勤労感謝の日）も平日10分（約3,200字）から15分拡大版（約4,800字）へ自動切替。さらに config/special_days.json で記念日カウントダウン、config/program_schedule.json で先々の専門家テーマや変更リクエストを管理し、resolve_tomorrow_preview() が明日の予告まで自動計算します。

🧠 28日＆90日の重複防止メモリ

data/topic_history.json と data/knowledge_log.json により、小平の街ネタは直近28日間、7人の専門家の解説キーワードは過去90日間（約3か月）同じテーマを繰り返さないよう build_dedup_context() が自動ガード。小春たちの「前に学んだあれですね！」という成長描写にも活用されます。

3. ステップ2 ― 3段階ハイブリッドAI制作 ＆ 自動ファクトチェック

src/generate_episode.py ・ src/plan_weekly_editorial.py

台本づくりは「Phase A：調査」「Phase B：台本執筆」「Phase C：ファクトチェック＆自動校閲」の3段階パイプラインで構成されています。それぞれ得意分野の異なるモデル gemini-4-hydrogen と gemini-4-neon をリレーさせています。

🔰 かみ砕きメモ：なぜAIが嘘をつくことがあるの？どう防いでるの？ 大規模言語モデル（LLM）は学習時の記憶をもとに自然な文章を紡ぐのが得意ですが、最新の地域イベント日程などを記憶だけで書くと、昨年の日付と混ぜてしまうハルシネーション（もっともらしい誤情報）が起きることがあります。そこで本番組では、まず Google検索グラウンディング（検索結果に根拠を置く仕組み） で今年の一次情報を調べ（Phase A）、執筆後に別の校閲AIがもう一度Google検索で裏取りをする（Phase C）二重の安全網を敷いています。

台本データは「読む用」と「しゃべる用」を分けている（JSON構造化出力）

Phase B の gemini-4-neon は単なる自由文章ではなく、JSON（ジェイソン）というプログラムがそのまま読み取れる設計図の形で台本を出力します。ここで非常に重要なのが、1つのセリフの中に画面表示用の text と音声合成用の tts_text の2種類を持たせている点です。

// episodes/YYYY-MM-DD/episode.json に保存される1セリフ分の構造 { "speaker": "koharu", "text": "小平駅南口から小川町まで、防災マップアプリを見ながら歩いてみたいです！", // 画面表示用（タグなし） "tts_text": "こだいらえき みなみぐちから おがわちょうまで、<short pause> ぼうさいマップアプリを みながら あるいてみたいです！<laugh>", // 読み上げ用（かな＋感情タグ） "style": "bright, cheerful, curious Japanese morning radio host", // 英語の演技ディレクション "pause_after": 0.34 // 次の人が話すまでの「間」（秒） }
Phase C の「小春キャラクター保護」校閲ルール： ファクトチェックAIは全セリフの日程・数値（耐震基準年や胸骨圧迫のテンポ100〜120回/分など）を厳しく検証し、誤りがあれば === FACT_CHECK_JSON === という修正パッチで該当行だけをピンポイント書き換えします。ただし、「小春が初心者としてお茶目に予想して、すぐ次のターンで平蔵や専門家が優しく訂正している箇所」は番組の大切な演出として残すよう設計されています。

4. ステップ3 ― 声の演技（Gemini 3.8 Flash TTS）＆ NumPy数式BGM・音響DSP

src/build_radio.py ・ src/bgm_synth.py

完成した台本JSONを受け取るのが src/build_radio.py と src/bgm_synth.py です。ここでは声の合成だけでなく、本物のFMラジオ局のミキサー卓と同じデジタル信号処理（DSP）をPythonとNumPy・FFmpegで行っています。

🔰 かみ砕きメモ：著作権フリー！BGMを「数式」から作ってるって本当？ はい！インターネット上の音楽素材をダウンロードするのではなく、src/bgm_synth.py の中でNumPy（ナムパイ）という数値計算ライブラリを使い、高校数学で習うサイン波（sin）を何重にも足し合わせて楽器の音色をゼロから合成しています。ローズ風の温かなエレキピアノも、朝のチャイムも、小鳥のようなベル音も、すべてプログラムが毎回44,100Hzの音の波として計算し、自然な残響（マルチタップ・リバーブ）をかけて生み出しています。

🎙 2話者・4ターン・420文字ブロック分割とキャッシュ

gemini-3.8-flash-tts のマルチスピーカーAPIは1リクエストで2話者まで自然な掛け合いを生成できます。_group_lines_into_blocks() が台本を「最大2話者・4ターン・420文字以内」に賢く束ねてAPI回数を抑え（15分番組でも約17〜25回程度）、さらに内容を SHA-256ハッシュ値 で .cache/tts_gemini/ に保存するため、台本の1行だけ直して再ビルドする際も変更行以外はAPIを再消費しません。

🎚 先読みダッキング ＆ ポッドキャスト基準 -16 LUFS

BGMがしゃべりを邪魔しないよう、_compute_ducking_envelope() が話し始める0.16秒前から先読みしてBGM音量を 0.36 から 0.11 へ滑らかに下げます（BGM自体も 4,200 Hz のローパスフィルタで声の帯域を空けています）。最後は FFmpeg で 70 Hz 以下の低域ノイズを除去し、世界標準のラウドネス規格 -16 LUFS に整えて 112 kbps MP3 と秒数台帳 manifest.json を書き出します。

5. ステップ4 ― サーバー不要で動く静的ポータル ＆ 同期字幕プレーヤー

src/build_site.py ・ docs/

多くのWebサービスでは裏側でデータベースやプログラムサーバーを24時間動かしますが、この番組は src/build_site.py がHTML・CSS・JavaScript・MP3だけの「静的ファイル群（docs/）」を丸ごと生成します。

🔰 かみ砕きメモ：なぜ「静的サイト」＋「HTML内JSON埋め込み」なの？ 通常のブラウザはセキュリティ保護（CORS制限）のため、ネットサーバーを通さずにPC上のHTMLファイルをダブルクリック（file://）すると外部のJSONファイルを読み込めません。そこで本サイトは、台本やタイムライン・カレンダー情報をすべてHTMLページの中の <script type="application/json"> タグへ直接埋め込んでいます。これにより、GitHub Pagesでの公開はもちろん、オフラインのWindowsパソコンで直接開いても100%同じように同期再生・検索ができます。

6. ステップ5 ― クラウド自動放送局（GitHub Actions・cron遅延対策・Secrets）

.github/workflows/daily-radio.yml ・ weekly-editorial.yml

自分のパソコンの電源を毎朝6時に点けておかなくても、GitHub Actions というクラウド上の仮想コンピュータ（Ubuntu Linux）が決められた時刻に自動で起動し、台本生成から音声合成・GitHubへの保存・GitHub Pages公開までを実行します。

🔰 かみ砕きメモ：2026年11月23日朝の遅延と「二重起動＋冪等（べきとう）設計」への強化 GitHub Actionsの無料枠の定期実行（cron）は、世界の多くの人が使う時間帯だと数十分〜数時間ほど実行キューで待たされることがあります。実際に11月23日朝は、従来の 06:35 JST 設定がキュー混雑で7時までに発火しない事象が確認されました。そこで同日、① 朝05:17 JST（約1時間40分の余裕） と 朝06:13 JST（予備キャッチアップ） のオフピーク2段構えへ変更し、② すでに当日のJSONとMP3が存在すればスキップする「冪等（何度走っても壊れない）チェック」を組み込みました。さらに日曜の編集長AIも 日曜昼12:17 JST に前倒ししてカレンダーページまで即更新します。
🔐 APIキーの安全管理（GitHub Secrets）： Gemini APIキーは課金や利用枠に直結するため、ソースコードや公開リポジトリには絶対に書き込みません。手元では .gitignore で除外された .env ファイル、クラウド上では暗号化金庫である GitHub Secrets（GEMINI_API_KEY）に保管し、実行中の仮想マシンのメモリ内だけに安全に渡しています。
